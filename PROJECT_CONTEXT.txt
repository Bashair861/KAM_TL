────────────────────────────────────────────────────────────────────────────────
WHAT IS THIS PROJECT?
────────────────────────────────────────────────────────────────────────────────
Aether KAM is an internal Key Account Management (KAM) portal for an IT services
company. Used by the KAM team to manage enterprise client relationships, track
account health, manage escalations, handle contracts, and grow accounts.

The app is built as a learning/portfolio project. It started fully static
(all data hardcoded in a JS file). It is now progressively wired to a real
Supabase backend with full read AND write operations.

USER ROLES & PERMISSIONS (ROLE_PERMISSIONS in kam-data.js)
────────────────────────────────────────────────────────────────────────────────
Three roles exist:

  CEO          → read: true,  write: false, scope: "all"
  Head of KAM  → read: true,  write: true,  scope: "all"
  KAM          → read: true,  write: true,  scope: "assigned"

- "scope: all"      = sees and can edit all accounts
- "scope: assigned" = KAM only sees accounts where assigned_kam_id = their profile id
- Write access controls whether Save/Edit/Add buttons are enabled in the UI
- Role is stored in the `profiles` table in Supabase
- Role is loaded into React via AuthContext → useAuth() → profile.role

IMPORTANT DECISIONS & PATTERNS
────────────────────────────────────────────────────────────────────────────────

1. DATA LAYER PATTERN (db.js)
   - All Supabase calls live in src/services/db.js
   - Mapper functions convert snake_case DB → camelCase JS objects
   - fetchAccount() uses Promise.all for 7 parallel queries (performance)
   - Components never import from @supabase/supabase-js directly
   - Mutations (useMutation) call db.js functions and also call logAccountChanges()
     in the same mutationFn so the history entry is part of the same operation

2. AUTH PATTERN
   - AuthContext is the single source of truth for auth state
   - session = Supabase Session object (null if logged out)
   - profile = row from profiles table (loaded by UUID or email fallback)
   - loading = true until first session check completes
   - Route protection is centralized in AppShell in __root.jsx

3. PERMISSION PATTERN
   - Every component that needs edit-gating: const { profile } = useAuth()
   - Then: const editable = ROLE_PERMISSIONS[profile?.role ?? "KAM"].write
   - Buttons use disabled={!editable}
   - "KAM" fallback = unknown roles default to most restrictive write scope

4. ENVIRONMENT VARIABLES
   - VITE_SUPABASE_URL      → browser-safe, used by src/lib/supabase.js
   - VITE_SUPABASE_ANON_KEY → browser-safe anon/publishable key
   - SUPABASE_SERVICE_ROLE_KEY -> server/Node only, bypasses RLS
     Used by seed.js and src/services/user-admin.js to create Supabase Auth
     invite users. NEVER put the service role key in a VITE_ variable.
   - File must be named .env.local (Vite convention — .env alone does not work)

5. KYC FIELD INITIALIZATION RULE
   - Each editable KYC field is initialized from ONE DB column only
   - Example: revenue field = account.revenue (not "account.revenue · ARR: $X")
   - Combining multiple columns into a single editable field caused doubling on save
   - If supplementary info needs showing, display it as read-only text separately

6. HISTORY LOGGING PATTERN
   - KYC save: computes diff between savedSnapshot and fields, logs changed fields
   - KAM assignment: logs "Assigned KAM" with old KAM name → new KAM name
   - KPI score: logs "Score: [title]" with old block.score → new score
   - editedBy is always profile?.name ?? "Unknown" (display name, not UUID)

7. account_history TABLE TYPE NOTE
   - accounts.id is type TEXT (not UUID) — it uses string IDs like "starlight"
   - Therefore account_history.account_id must also be TEXT
   - This is different from most other FK columns which use uuid

8. KPI DATA STORAGE
   - health_scores.kpi_data (jsonb) stores the full KpiSection[] array
   - On KpiEditorModal open: loads from block.kpiData if present, else seeds from metrics,
     else seeds one default section (new accounts with no metrics)
   - On save: upserts health_scores row (INSERT if new, UPDATE if exists) + full sections
     array saved to kpi_data. Existing metric rows updated by UUID if present.

9. NEW ACCOUNT DEFAULTS
   - health: 50, trend: 0, status: 'healthy', retention_risk: 'Low'
   - growth_upside: 0, white_space_count: 0, is_startup: false
   - health_scores rows are pre-populated for all 8 areas on insert
   - contract_details reference row is created on insert for type/duration/renewal date
   - KPI editor still handles missing legacy rows by inserting on first save
   - Score bars derived from kpi_data jsonb when health_metrics rows are absent

10. DERIVED METRIC BARS PATTERN
    - fetchAccount block() helper checks: if health_metrics is empty AND kpi_data exists,
      compute each section's score as (checked weight ÷ total weight) × 10
      and use section name as label → passed to mapHealthBlock as derived metrics
    - These show as progress bars in ScoreBlock without needing DB metric rows
    - Derived metrics have id: "derived-N" (not real UUIDs) — do not use for updates


────────────────────────────────────────────────────────────────────────────────
11. PROJECT CHARTER SHEET UPLOAD PATTERN
    - Charter upload is client-side only: accounts.$accountId.jsx imports JSZip,
      validates .xlsx files, and parses xl/sharedStrings.xml + worksheet XML in browser.
    - It is not OCR and does not upload/store the workbook in Supabase or on the server.
    - Upload controls are role-gated by the existing editable permission and disabled
      while the workbook is being read.
    - Label matching uses KYC_FORM_FIELDS labels + aliases. It supports both
      "Label: value" cells and nearby right/below/diagonal value cells.
    - Extracted values are filtered through field-specific validators so template
      labels, instructions, placeholders, and generic words are not autofilled.
    - CharterMappingDialog is mandatory review: only checked rows with extracted
      values are applied. Rows can show Yes, Local, No value, or No match.
    - Apply Selected updates local KYC state only. DB-backed values are persisted
      later through the existing Save KYC flow and history logging.
    - The dialog stays open after Apply Selected so the user can review the success
      message, apply another selection, or close manually.
    - Local-only charter values such as accountStatus and stakeholdersInfo update
      savedSnapshot immediately because they are visible context but not DB-backed.
    - Current Charter extraction intentionally excludes Account Details fields
      (contractRenewalDate, contractDuration, linkedinUrl, websiteUrl), even though
      those fields exist in KYC_FORM_FIELDS for manual edits and Salesforce sync.

      KYC, Account Details, Account's Linkedin Summary, Account's Website Summary,

    - The protected last three sections are not changed by the field picker.
    - The configurable list is driven by OVERVIEW_SECTION_FIELD_GROUPS in

    - The picker also exposes other account-level fields that are not part of the

    - KYC selectable fields include accountStatus, industry, business, description,

    - Account Details selectable fields include tier, operational status, contract

    - Backend/system fields are intentionally hidden from Edit Sections:

13. SYSTEM-WIDE VALIDATION PATTERN
    - Shared validation lives in src/services/validation.js.
    - Validate at the service layer before writes, even when the UI already has
      form controls. This protects browser forms, server functions, and integrations
      consistently.
    - Prefer normalization over rejection for harmless formatting differences:
      trim text, lowercase emails, add https:// to plain domains, parse numeric
      strings, and remove blank optional values.
    - Reject unsafe/control/script-like text, empty required fields, symbol-only
      garbage, invalid email/phone/URL/date values, and out-of-range numbers.
    - For integrations, skip invalid optional external values where possible instead
      of clearing existing trusted values. Required invalid data should fail with a
      readable validation error.
    - Hidden or absent fields must not block manual saves. Only validate hidden
      fields when they are explicitly supplied by a visible UI control or an
      integration payload.
    - Existing mutation error handlers should surface ValidationError.message to
      users. Keep messages specific and human-readable.
    - No required DB migration was introduced with Phase 4.11. Optional PostgreSQL
      NOT VALID check constraints may be added later for defense-in-depth after
      auditing existing production data.
